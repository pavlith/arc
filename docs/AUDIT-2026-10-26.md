## 1. Выводы

Arc уже является **реализованным фундаментом распределённой self-hosted платформы**, а не только набором архитектурных документов. Основные компоненты Foundation существуют в коде: единый Core с Identity/Access/Fabric/Runtime, отдельный Gate, SDK, NATS/JetStream, доменные Task и Notify с собственными SQLite-файлами, GORM/Gormigrate и интеграционными guardrails. Но это всё ещё **M0 — Foundation**, а не завершённый пользовательский продукт и не production-ready система.

**Стратегическая рекомендация:** не переписывать SDK и не дробить Core; исправить выявленные проблемы, довести bootstrap и M0-07 до `Integrated`, после чего сделать первый полезный пользовательский поток M1 через Svelte 5 UI и Gate. Полная матрица устойчивости, нагрузок, совместимости и безопасности остаётся M7, как предусмотрено текущими нормативными документами.

## 2. Реализация по компонентам

| Компонент | Подтверждённая основа | Следующий шаг |
| --- | --- | --- |
| **Identity** | Sessions/login/refresh, principals, Service Accounts, delegation, invocation verification, signed JWT/proof | Key lifecycle, администрирование и эксплуатационные процедуры |
| **Access** | Ресурсы, ACL roots, grants, allow-only permissions, online проверка прав и lifecycle | Стабилизировать контракты, не вводить общий policy DSL |
| **Fabric** | Approved manifests/artifacts, установки с подписью, leases, discovery, route snapshots, event permits | Безопасный installer/upgrade-процесс |
| **Gate** | HTTPS ingress, sessions/Bearer auth, CORS/CSRF, signed routes, HTTP → typed RPC, rate/body/deadline limits | Отдельный production deployment, браузерная модель auth, позднее WS/DAV |
| **Task** | Proof-сервис create/get/list, root/workspace ACL, command replay, audit, transactional outbox | M1: Task/Projects/Views, UI и совместное использование |
| **Notify** | Atomic inbox/effect, subscriptions, delivery intents, stable provider retry key, fake provider | M1: реальные каналы и пользовательский API |
| **Runtime** | Desired deployments + optimistic concurrency по revision + авторизация | M0-07: модель nodes/templates/operations, fake Agent, метрики/guards |
| **SDK** | Registration/leases, typed RPC, contracts, auth, events, modules, lifecycle, bootstrap | Стабилизация API и проверка расширяемости без нового универсального слоя |

### Структурные принципы, которые стоит сохранить

- **Отдельные процессы**, но **один Go module**: `services/<owner>/`, `cmd/arc-<owner>/` и общая `sdk/`. Отдельный процесс не требует собственного `go.mod`.
- Core объединяет Identity, Access, Fabric, Runtime; между этими модулями допускаются прямые Go-вызовы и одна Core SQLite. Нет причины превращать их в отдельные сетевые микросервисы.
- Доменные сервисы владеют своими данными. SQL-запросы в чужой owner DB не допускаются; обмен через RPC/events.
- Gate не является владельцем ACL, бизнес-логики, произвольных маршрутов или БД. Проверка прав повторяется на стороне сервиса.
- Подписанные manifest/digest/operation/proof и fail-closed авторизация имеют приоритет над удобством discovery.
- SQLite подходит исходной single-host owner-local модели; multi-host independent replicas и network FS не поддерживаются.
- NATS/JetStream отвечает за транспорт; SDK не должен становиться полным форком `nats.go/micro`.

См. [`services/README.md`](../services/README.md), [`sdk/README.md`](../sdk/README.md), [`docs/sqlite-gorm-migration.md`](sqlite-gorm-migration.md).

## 4. Подтверждённые проблемы и риски

### P0. Падающий `rename-preview` (подтверждённая ошибка CI)

[Workflow run 40309465698](https://github.com/pavlith/arc/actions/runs/40309465698) на `8a22253d` провалился **после** успешного шага применения одноразового rename — на `go test -race ./...`.

Симптомы логов:
- `TestOwnerMigrations/task`: `missing owner table "task"`;
- `TestOwnerMigrations/notify`: `missing owner table "notify"`;
- `TestSQLiteInboxAndDeliveryStableKey`: `no such table: notify`;
- `TestSQLiteTaskCreateReplayAtomicOutbox`: `no such table: task`.

В реальных миграциях бизнес-таблицы называются `tasks` и `notifications`, а одноразовый [`rename_services.py`](../.github/scripts/rename_services.py) содержит слишком широкие текстовые подстановки, включая `TASKS`, `"tasks"` и `"notifications"`. Повторное применение преобразования нарушает различие между **service identity** и **business table/entity**. Ошибки фиксируются в preview; остальные основные CI текущего commit прошли.

**Рекомендация:** считать migration имен `task/notify` завершённой, удалить одноразовый скрипт и [preview workflow](../.github/workflows/rename-preview.yml), оставить regression-тесты схем, гарантирующие сохранение `tasks`/`notifications`. Не запускать массовый rename повторно. Закрытие: зелёный CI без script-induced изменения схемы.

### P0. Нет самостоятельного `cmd/arc-core` (deployment gap)

[`services/core/service.go`](../services/core/service.go) композирует четыре Core-модуля, но в проверенном `cmd/` нет `arc-core`; [`compose.yaml`](../compose.yaml) описывает NATS/migrators/smoke, а не полный автономный Core deployment. Проверяемая интеграционная цепочка поднимает Core и Gate в тестовом host, Task/Notify как отдельные бинарники.

**Рекомендация:** добавить `cmd/arc-core` с безопасной загрузкой всех trust/signing keys, полной конфигурацией NATS/SQLite, явным startup после migration, readiness, signal handling и shutdown. Отдельно собрать воспроизводимый Compose/systemd bootstrap Core + Gate + Task + Notify с независимыми credentials и owner volumes. Не путать это с M6 Docker Agent: базовые инфраструктурные сервисы остаются unmanaged.

Критерий: чистая установка и e2e без объединённого тестового host.

### P1. Структура в архитектуре не соответствует текущему коду

[ARCHITECTURE.md `11](ARCHITECTURE.md#11-структура-кода-ориентир-не-предписанные-go-module-boundaries) всё ещё содержит ориентиры `sdk/go/`, `internal/core/`, `services/tasks/` и корневую `migrations/`. Реальный код использует `sdk/`, `services/core`, `services/task`, `services/notify`, owner migrations. В `8 и некоторых нормативных примерах остаются старые plural названия, в том числе устаревший `sdk/cmd/arc-gate`.

**Рекомендация:** обновить структурную карту, имена deployment и команды запуска; явно различать имя сервиса `task`, Go package `tasks`, бизнес-таблицу `tasks` и имена API operation. Не переписывать весь двухтомный нормативный набор только ради путей.

### P1. Сетевой I/O внутри SQLite write transactions

В [`services/notify/modules/delivery/gorm.go`](../services/notify/modules/delivery/gorm.go) `Provider.Send` вызывается в транзакции с заранее захваченным write lock. В [`sdk/events/gorm_delivery.go`](../sdk/events/gorm_delivery.go) синхронный `js.Publish` происходит под транзакцией outbox; аналогичный предмет для оценки — вызов Access RPC внутри task grants command ([`services/task/modules/tasks/service.go`](../services/task/modules/tasks/service.go)). [`sdk/database/sqlite.go`](../sdk/database/sqlite.go) ограничивает соединения `MaxOpenConns(1)`, усиливая риск задержек других операций владельца.

Это **архитектурный риск, не доказанная эксплуатационная авария**. Модель M0 проходит smoke, но внешний timeout может длительно удерживать writer и увеличивать tail latency; в случае grants нужно отдельно учитывать distributed partial commit.

**Рекомендация:** короткая транзакция claim/lease → внешняя операция → короткая finalize/reconcile транзакция. Для publisher обязательны stable event IDs и at-least-once; для delivery — stable provider idempotency keys; для cross-service grants — подтверждение и reconciliation. Не заявлять exactly-once внешних эффектов.

### P1. Сквозная observability неполная

[`sdk/telemetry/telemetry.go`](../sdk/telemetry/telemetry.go) логирует service/module/operation/kind/duration/error_code, но не извлекает и не записывает `request_id` или `traceparent`. Для распределённого пути через Gate, Identity, Access, Task, JetStream и Notify это критично для диагностики.

**Рекомендация в M0-07:** structured logs с корреляцией request/trace и безопасными actor/instance identifiers, RPC latency/ошибки, lease/permit denials, lag и retry для outbox/inbox, состояние Runtime revision, без raw payload/credentials/JWT/cookies.

### P1. Перед UI формально развести browser и API authentication

[`services/gate/modules/http/auth.go`](../services/gate/modules/http/auth.go) реализует Secure/HttpOnly cookies/CSRF, но `login`/`refresh` также возвращают `access_token` в JSON. Поддержка Bearer для CLI/API — нормальная задача; сам факт JSON-ответа не является доказанной уязвимостью.

**Рекомендация:** определить браузерный контракт с HttpOnly session + CSRF без необходимости сохранять Bearer в JS, а отдельный token flow оставить для API/CLI, после чего проверить Origin/CSRF, session renewal и logout в браузере.

### P2. CI содержит дублирование и изменяет рабочее дерево

Сейчас есть отдельные SDK, layout, SQLite и M0 workflow. В [`services.yml`](../.github/workflows/services.yml) выполняется `gofmt -w` вместо чистой проверки; это может маскировать неотформатированный исходник в runner.

**Рекомендация:** CI только проверяет форматирование; для PR выделить быстрые build/vet/targeted tests, для изменения security/transport/contracts — обязательные M0 guardrails, для большого CI — отдельные integration runs. Ввести статическую проверку направления импортов: SDK не импортирует бизнес-реализации, domain services не импортируют чужие SQL repositories.

### P2. Долговременное владение межсервисными API

Notify использует [`services/task/api/v1`](../services/task/api/v1) для события; это **нормально в монорепозитории** и не запрещает отдельный runtime deployment. На более позднем этапе имеет смысл экспортировать только стабильный versioned contract, не допуская импорта Task internals/ORM другого сервиса.

### Отложено сознательно (не дефекты M0)

Реальные email/Telegram/push providers, UI, Pages/Projects, WS/DAV адаптеры, полноценный Agent, multi-host orchestration, recovery/load/chaos/client compatibility и M7 verification. Не нужно искусственно объявлять их блокерами M0-01–M0-06, если они явно отложены спецификацией.

## 5. Runtime и M0-07 — следующий функциональный этап

[Issue #8: M0-07](https://github.com/pavlith/arc/issues/8) остаётся `open` / `status: backlog` / `P0`. В коде уже есть:
- [`services/core/modules/runtime/module.go`](../services/core/modules/runtime/module.go): `Desired`, `Put/Get`, онлайн авторизация и fail-closed;

- тесты на конфликт ревизий и отказ при отсутствии разрешения.

**Это только часть M0-07**. По [архитектурному контракту `7](ARCHITECTURE.md#7-runtime-control-и-arc-infrastructure-agent--контракт-m0m6) требуются RuntimeNode, RuntimeTemplate, RuntimeOperation/observations/revisions, approved metadata, `RuntimeProvider` interface, fake Agent contract tests, guardrails forbidden template/bootstrap target и сквозная telemetry.

Целевой M0-07:
1. Добавить минимальную owner-local модель nodes/templates/operations/observations и typed DTO/interfaces в Core.
2. Определить протокол pull-current-desired с подписанными ответами, revision, target node, lease/expiry и independent Agent validation.
3. Реализовать **fake** Agent с запретами: bad proof, stale revision, forbidden image/template, bootstrap target, cross-node scope, duplicate replay.
4. Добавить structured logs/metrics по `request_id` и `traceparent` и минимальный contract smoke.
5. Убедиться, что `arc-core`/Gate/Task/Notify можно поднять независимо, а реальные Docker socket и executor остаются **M6**.

Не добавлять в M0 scheduler, rollout engine, реальный Docker RPC, multi-node placement или полный M7 chaos/hardening.

1. Не вводить объединённый гигантский `Platform Service` вместо хорошо разделённых Core/SDK/Gate.

3. Не переписывать SDK заново и не форкать весь NATS Micro.
