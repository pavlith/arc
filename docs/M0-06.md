# M0-06: Task → Notify

Воспроизводимый локальный запуск (Go, PostgreSQL `initdb/pg_ctl/psql`, Python 3,
`nats-server` в PATH; выполнять обычным пользователем):

```sh
make m0-06-smoke
```

Скрипт создаёт временные PostgreSQL и TLS/NKey NATS, применяет все миграции дважды,
запускает M0-01–M0-05 guardrails и полный вертикальный smoke с race detector.
Fixtures в `services/task/integration_test.go` создают пользователей/workspaces,
ServiceAccounts, подписанные approvals, Reserve/domain receipt/Activate roots и
реальные Access grants. Task и Notify запускаются отдельными бинарниками;
Core и HTTPS Gate работают в интеграционном host с реальными NATS RPC. Mock
Identity/Access, SQL или JetStream в этом сценарии нет. После теста окружение удаляется.
Обычный `go test ./...` без DSN явно пропускает интеграцию.
`ARC_TEST_TASK_ONLY=1 make m0-06-smoke` оставляет миграции/M0-01 и M0-06 для
локальной отладки; окончательный прогон и CI выполняются без этого флага.

Самостоятельные процессы:

```sh
make m0-06-build
cd sdk
go run ./cmd/arc-task -config /path/to/tasks.json
go run ./cmd/arc-notify -config /path/to/notifications.json
```

Примеры конфигурации: `deploy/task/config.example.json` и
`deploy/notify/config.example.json`. DSN читается из отдельного secret file;
пользователи — `arc_task` и `arc_notify`, с доступом только к собственной
схеме. Общий PostgreSQL instance не даёт прав читать чужие/Core таблицы. Service
seed — 32 raw Ed25519 bytes, mode 0600. Core public key — JSON base64 string.
Core private key и operator key доменным процессам не передаются.

Для уже подготовленного Core/deployment: `make m0-06-up` использует
`compose.m0-06.yaml`, отдельные read-only mounts `.secrets/m0-06/task` и
`.secrets/m0-06/notify`. В каждом — `config.json`, `database.dsn`,
`nats.seed`, `service.seed`, `core-public.json`, `ca.crt`. Файлы должны читаться
контейнерным пользователем `arc`. Это запуск доменных процессов, не замена
operator installation; полный автоматический bootstrap предоставляет smoke.

Task manifest/schema находятся в `services/task/contract/`, Notify artifact —
`services/notify/contract.go`. Установка обоих идёт через `fabric.Core.Approve`
с operator signature. `subscriptions` Notify installation фиксирует точные
Task provider/digest/subject/durable. `ctl.arc.fabric.event_permit` проверяет их
перед pull и каждым effect; отсутствующая или отозванная approval запрещает delivery.

Operation ID не повторяет API major: `task.task.create/get/list`, subject
`rpc.task.v1.task.create/get/list`. Это существующее нормативное правило SDK:
`rpc.<service>.v<major>.<operation suffix>`. Создание по HTTP:

```text
POST /api/v1/task/workspaces/{workspace_id}/roots/{acl_root_id}/tasks
Authorization: Bearer <HTTP login access token>
Idempotency-Key: <stable client key>
{"title":"Proof"}
```

GET на тот же URL с `?limit=10` возвращает максимум 100 собственных задач;
GET `.../tasks/{task_id}` читает конкретную разрешённую задачу. Root/workspace берутся
из подписанных route bindings. `auth.workspace_from` связывает workspace с
invocation exchange. Task проверяет фактическую связь task/root/workspace в своей
БД, затем выполняет онлайн Access.Check, включая command replay. Внутренний
`task.roots.grants` имеет HTTP exposure=false и предназначен только для approved
ACL provisioning; Access отдельно проверяет фактические полномочия на grant.

`identity.v1.invocations.verify` — закрытый authenticated RPC для recipient service.
Core выводит audience из зарегистрированного ServiceAccount, проверяет JWT,
request proof, nonce и текущую session/membership. Ответ подписан Core и связан
с SHA-256 полного исходного envelope, subject, audience и сроком 5 секунд.
Это позволяет сервису не получать Core DB credentials. Разрешение этого RPC и
exchange_service выдаётся только точным ServiceAccounts через signed policy.

Task транзакция фиксирует task, audit, command result и outbox вместе. Publisher
использует `Delivery.PublishBatch`; event содержит только task/workspace/root IDs,
исходный event_id и traceparent, без title/user/секретов. Сбой publisher оставляет
committed outbox для retry. Replay с другим payload возвращает CONFLICT.

Notify получает адресатов из operator-managed `subscriptions` своей БД
(активная запись workspace/root/recipient). Сам процесс имеет только SELECT на
адресацию. Event не выбирает recipient и не предоставляет права читать Task.
Inbox, notification и outbound intent фиксируются одной транзакцией через
`Store.Consume`; `Delivery.Pull` делает ACK после commit. Durable и exact event/DLQ
subjects не зависят от входящих данных. В M0 installer создаёт stream `TASK`
на `evt.task.task.created.v1` и DLQ stream; consumer создаётся лениво с explicit ACK.
Scoped NKeys для изолированного окружения создаёт `arc-m0-06-credentials` после
базового bootstrap; этот helper предназначен только для временного dev/test broker.

Fake provider получает сохранённый SHA-256 ключ от notification/recipient/channel.
Timeout после внешнего эффекта повторяет тот же ключ; SQL commit не делает внешнюю
отправку exactly-once. Реальный неидемпотентный provider может отправить повтор.
Delivery intents не удаляются автоматически. Реальные email/Telegram/push, UI,
пользовательская модель подписок и расширенный Task/Kuayle — M1. Полная crash,
replica/reconnect, performance/load и recovery матрица — M7; readiness этого этапа
после guardrails — Integrated, не Verified.

## M0 acceptance evidence — 2026-10-26

Issue: [#7](https://github.com/pavlith/arc/issues/7).
Successful isolated CI: [M0-06 guardrails run 40268413044](https://github.com/pavlith/arc/actions/runs/40268413044),
at commit `ec905da4c04171f725b9a83af08fd152421f1ba7`.

- Login → HTTPS Gate → Task → online Access/Identity → task/audit/command/outbox
  transaction → JetStream → Notify inbox/effect/intent → fake delivery:
  **passed** with domain binaries and real service-specific DB/NKey credentials.
- Same command replay, changed-payload conflict, outbox and inbox transaction
  rollback, concurrent inbox replay and JetStream redelivery: **passed**.
- External retry preserves the persisted deduplication key; uncertain provider
  timeout does **not** claim exactly-once external delivery.
- Fail-closed: missing publisher/consumer permits; wrong provider, contract
  digest, event subject or durable; revoked Notify approval while the
  consumer is running leaves a newly published event pending with **no inbox
  or notification effect**. Contract revocation is irreversible for that digest:
  the test intentionally runs after positive consumer checks and never
  attempts to restore a revoked approval.
- Fail-closed: cross-schema access, untrusted actor, forged JWT/proof,
  revoked membership/grants, unavailable Access/Fabric/Identity; no task
  mutation during Core outage. Publisher failure leaves committed outbox
  pending for retry.
- `verify-changed.sh --all`, Go build, Go vet and M0-01 through M0-06
  regressions passed in the CI run.

### End-to-end measurement (running consumer)

Ten sequential create requests each waited until the matching task event's
notification **and persisted fake-provider delivery intent** were complete.
Sample reported from that successful GitHub-hosted run:

| Samples | p50 | p95 | max |
| ---: | ---: | ---: | ---: |
| 10 | 800.230351 ms | 826.270923 ms | 826.270923 ms |

This measures **HTTP create → notification → fake delivery**, not the initial
login, cold consumer start, isolated RPC overhead or throughput. The test
observes completion at 25 ms polling intervals; producer and consumer
workers tick every 100 ms. Values are CI-environment samples, not an
operational SLO. Reproduce with `make m0-06-smoke` and find the
`running-consumer create -> notification -> fake delivery` line in
`TestM006` output.

**Acceptance:** the narrow M0-06 vertical proof is complete. Full Kuayle
Task/Notify migration, external providers, UI, crash/recovery, replica
and load/performance validation remain explicitly deferred to M1/M7.
This evidence does not promote the wider platform from **Integrated** to
**Verified**.
